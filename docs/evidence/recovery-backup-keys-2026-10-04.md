PostgreSQL 17 一次性容器。复用现有 Java 迁移器、恢复 fixture、冻结输出、审批

备份文件只留在一次性容器内，不复制到桌面、工作区或日志。

测试配置要求 CODELENS_INTEGRATION_TESTS=true 与 CODELENS_BACKUP_TESTS=true；
工具创建自己的目标，不接收外部库或容器参数。子进程有超时与输出大小限制，不

## 完整快照与正确密钥

第一类测试构造暂停、完成和拒绝三种合成审查：

- 对所有 public 表按表名/行内容排序，再对 JSON 汇总做 SHA-256；源和恢复库
  完全一致，检查前后指纹未变。fixture 在备份时静止，不冒称实时源库的多次
  指纹采集也是一致快照。
- 模式清单 001–021、迁移 checksum、冻结记录身份/密文/内容哈希一致。
- 另行从测试内存提供原发布密钥，原冻结正文和 summary 可读；错/缺密钥拒绝，
  错误没有密文或底层解析详情，不补造、不重新分析。
- requested/pending、denied 及限定理由、committed 与本地结构结果保留。
- 快照已经包含的 consumed 审批，再登记触发数据库唯一约束拒绝；错审批密钥
  与过期审批也拒绝。
- 恢复后的冻结表/审计表 UPDATE 仍由不可变触发器拒绝。
- 检查所有恢复的业务行，不含测试运维 bearer、发布/审批密钥或审批令牌。
  验证用密钥独立于数据库备份提供，不是从备份取出的。

## 明确反例：旧备份不能记住未来的审批消费

第二类测试先备份，再在源库消费审批，然后检查旧备份的恢复库：

1. 源库已存在 requested，恢复库却返回 NOT_FOUND，原 Binding 仍相同。
2. 保留旧审批签发密钥时，尚未过期的旧令牌验证通过，并能在恢复副本再次登记。
   这是故意在合成副本写入审计的反例，不运行实际恢复，不修改远端。
3. 换用全新独立审批密钥后，旧令牌拒绝；新签发令牌可验证，随机审批 ID 不同。
4. 原发布密钥仍可解密原冻结输出，不因审批密钥变更而损坏历史结果。

因此，“单次审批”只覆盖保留的数据库历史，不能被宣称为跨备份回滚保证。
恢复必须隔离所有写入者、保持 API/Worker/恢复入口关闭，单独恢复历史发布密钥，
并通过受保护运维流程生成全新审批签发密钥，以废止全部旧审批。尚未实现自动
防回滚/密钥轮换，不能仅凭本测试开放恢复或盲目重启还原队列。

备份之后的远端副作用、撤销和数据删除也可能不在旧库；需重新调查、只读核验
并重新应用授权的保留/删除控制。报告本身不授权重排、发布或重新签发。
