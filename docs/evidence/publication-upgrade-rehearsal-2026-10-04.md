# 发布协议升级：隔离备份恢复演练（2026-10-04）

## 结果

新增可重复的运维入口 `npm run ops:rehearse-upgrade`。使用一次性 PostgreSQL 17、
随机容器名、随机本机端口和生成的临时测试密码；没有连接当前公网数据库，没有运行
API/Worker，没有 GitHub 请求，没有修改正在运行的 java.13 镜像或配置。

演练复用现有 Java migration 模式，不另写迁移执行器。临时旧清单是原迁移文件
001–019 的原字节副本，新清单为现有 001–020。

## 实际验证

修订后的演练脚本执行成功，输出 `status=passed`：

1. 建立 schema 019，写入模拟历史审查、失败队列、publication、三个发布操作日志
   和仍被占用的摘要记录。所有内容均为模拟数据，不执行这些任务。
2. 在容器内使用 `pg_dump -Fc` 备份；在另一个独立数据库通过 `pg_restore`
   恢复。对所有 public 表的表名和按行内容排序的 JSON 做 SHA-256，一致性检查通过。
3. 使用 Java 迁移器升级恢复库至 020，旧业务表所有行仍一致；新增冻结表为 0 行，
   不补造旧输出、不删锁、不重新排队、不重新发布。迁移清单记录数量为 20。
4. 再运行迁移，新库所有行指纹不变。
5. 旧版清单明确报 `database contains an unknown migration: 020_...`，拒绝新版库。
   检查的是指定拒绝原因，不把任意连接失败当作验证成功；拒绝后所有行仍不变。
6. 原 schema 019 源库指纹未改变。两个模拟数据库及容器内备份随一次性容器删除；
   临时迁移目录解析绝对路径并限定其父目录/前缀后清理，清理报告成功。

## 安全边界与回归

脚本仅接受显式 `--isolated-fixture`，不接受外部库、容器或凭据参数；两个参数拒绝
回归测试通过。子进程环境、完整日志、SQL 行和密码不打印。迁移/备份是隔离维护
操作，没有把外部请求放入应用事务。类型检查通过。

最终回归：辅助工具 18 个套件、92 项全部通过；密钥扫描 333 个文件、0 发现，
diff 格式检查通过。本轮没有修改 Java 业务代码。公网容器仍健康运行，本机
`/readyz` 返回 200；没有遗留演练容器。
