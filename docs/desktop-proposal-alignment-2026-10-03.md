也不改变 Phase 0/1 的退出条件。外部项目机制仅作为待核实设计参考，

## 保留与采用

- 保留现有 Java 生产服务、PostgreSQL 队列、Java 全仓库语义索引、证据链和审计。
  不因候选文档面向 Go 岗位而重写生产逻辑；Go 路径仅维护共享数据库兼容性。
- 采用“版本化审查、显式覆盖缺口、持久化预算与失败状态、先验证再发布”的设计方向。
- 不引入新的 Redis/outbox 双写链路；Java 任务和入队保留在同一个数据库事务内。
  本轮迁移 017 已将 Webhook receipt 与任务事务合并，支持原始请求重投，
  不保存原始 payload、不冒充自动 inbox 重放。
- 保留已经实现的复用候选调查和审计决策，后续补局部补丁预览，不另建平行方案生成器。
- 自动化、变异样本可用于工程回归；不能冒充独立 gold 或证明人工 Review 时间下降。

## 本轮源码发现与修复范围

`JdbcStore`、TypeScript store 和 Go rollback store 原有去重键不包含 Base SHA；
Java `ReviewEngine` 分析前与发布前仅检查 Head SHA。目标分支前进而 Head 不变时，
会错误复用历史任务或继续发布旧 Base 的结果。

本轮将入队键统一为：

`repository + PR + base + head + enqueue_config_hash + pipeline_version + request_key`

`enqueue_config_hash` 保存入队输入，应用不再用运行时配置更新它；原有 `config_hash`
仍记录执行时解析出的策略。生产入口目前传入 `default-v1`，**这不是完整有效配置的内容摘要**。
模型提供方、仓库管理策略等配置变更后自动触发重审，仍需实现完整快照契约。
当前仓库 ID 也不替代安装授权校验或未来租户/安装生命周期隔离。

Java Worker 检查任务载荷与数据库版本一致，读取 diff 后再确认远端 Base/Head，
发布前再次确认，任一变化即标记 stale 且不发布正常结果。
这不是 GitHub 上的原子比较并发布：最后检查后的远端变化仍可能发生。
Go/TypeScript 的存储兼容已同步；两条历史 Worker 不承诺新增的 Java 双版本检查。

## 迁移与发布约束

新迁移 `015_review_identity.sql` 在迁移器的单一事务内回填字段并替换唯一索引。
历史入队配置已被覆盖时无法还原，只能以现存 `config_hash` 回填；历史任务不能视为
与新入队键完全等价。Java pipeline version 升为 `java.7`，避免复用旧版本任务。

该迁移需要维护窗口：停接收并停旧 Worker，备份，在预生产验证后运行迁移，
再启动本轮更新的服务。索引创建/回填会锁表，大数据量需单独设计在线迁移。
不支持旧二进制与新唯一约束混跑；旧查询指定的冲突目标已不存在。
发生问题优先回滚到支持新 schema 的代码，不擅自回退数据库或恢复旧索引，
因为新版可能已经产生旧约束不允许的合法记录。

随后迁移 `016_job_lease_fencing.sql` 增加租约字段和 processing 状态约束；
旧 processing 行沿用 locked_at + 15 分钟的过期时间，新的 Java 认领使用 120 秒。
生产 pipeline version 升为 `java.8`。此次必须停所有旧 Worker 后迁移和启动新 Java Worker。
历史 Go Worker 不支持该租约协议，其认领将违反状态约束；历史 TypeScript Worker
也未实现此次 fencing。它们不能作为当前 schema 的生产回滚 Worker。

迁移 `017_atomic_webhook_receipt.sql` 新增处理结果和 nullable run 外键，
不回填虚构的历史处理结果，也不改变 payload 保留策略。必须停止旧 API 后升级新 Java API。
历史 Go/TypeScript API 没有本轮接收原子性保证，不允许混跑。
