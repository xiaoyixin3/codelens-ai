# Java 后端量化证据协议 v1

记录日期：2026-10-07。先固定本协议，再测量；结果无论好坏均归档。此实验不关闭 Phase 0 / Phase 1 退出门槛。

## 测量对象

1. 生产 `JavaSemanticAdapter`：同一冻结 Base / Head 的全量 Head 与增量 Head，预热后各 5 次，交替顺序，记录每次耗时、索引覆盖与语义集合一致性。材料为 CodeLens 已提交版本和 250 文件受控 Java 仓库，不使用未独立标注的封存 holdout。本轮不执行输入仓库的构建、测试、插件或代码。
2. `SemanticIndexService` + 既有 `FileSemanticSnapshotStore`：记录首次计算加落盘和同一快照 5 次读取的耗时；这是文件存储路径，不代表生产 PostgreSQL 缓存吞吐量，也不代表 OS 冷缓存。首次仅 1 次，不能据此计算稳健的加速比。
3. 独立回环端口上的现有本地 HTTP 审查入口：64 文件受控仓库、1 次预热、1/2/4/8 并发，每组 10 波，共 150 次正式请求。每波完成后进入下一波。单请求 130 秒，整个执行器 12 分钟上限。该入口只允许 1 个活动分析，409 是过载保护，不算成功吞吐量。成功、拒绝、失败分别统计 P50/P95/最大时延；低样本尾延迟只是描述性数据，不是生产 SLO。
4. 现有租约、原子接入与发布安全回归：实际运行既有测试，报告通过、失败、跳过；Mock 测试不能标成数据库并发压测或真实 GitHub 故障演练。

## 固定口径

- JVM 堆上限 512 MiB（不是进程总内存上限）；记录 CPU、逻辑处理器、系统内存、Java/Node、适配器版本、JAR 哈希、Git SHA 和工作区源码哈希。
- 索引耗时不包含 Git 物化与预先检测构建模型；分别记录工作区物化时间。HTTP 耗时包含接入、Git 读取、Java 子进程启动、两端全量解析和上下文构造，不包含浏览器绘制、LLM 或远端发布。
- 索引输出同时比较文件哈希、符号记录、关系记录的集合；增量有缺失/多余结果时，速度优势不能作为正确优化成果。
- 允许缓存预热，不清空系统页缓存；全量与增量都在同一进程内预热。完整记录顺序与单次样本，不只保留最快一次。
- 并发波次是闭合突发实验，不宣称持续开放到达流量下的最大 QPS；吞吐只按成功完成数 / 整组墙钟时间计算，另列拒绝数。
- 不把代码行数、关系数量、测试数量或 409 的快速返回写成产品准确率或真实 Review 提效。

## 安全边界与停止条件

- 不对公网、GitHub、真实用户任务或现有 4310 工作台施压；临时工作台只监听随机回环端口，不读取 `.env`，不调用模型。
- 不启动 Docker Desktop：它可能自动恢复既有公网试用容器。本机 Docker 引擎当前不可用，数据库压测记为未执行，不借用旧数据库。
- 只在独立性能输出目录生成受控 Git 仓库和快照缓存；不改输入仓库，不清理用户工作区，不读取封存 gold/holdout 答案。
- 每个子进程有超时；请求发生意外 400/500、索引集合不一致、服务退出、超时等情况保留失败证据，不删除样本或自动增加有利样本。
- 该测试不执行真实第三方代码。修改性能测试工具不能改变生产解析和拒绝策略。

## 复现

在项目目录执行 `mvn -q -DskipTests package`，然后执行 `node --import tsx scripts/performance-evidence.ts --output=<独立输出目录>`。脚本复用已编译生产类和既有本地审查入口，输出机器可读原始样本与机器环境。

可写入简历的数据需要附样本、对照、环境、边界。Phase 0 的真实人工 Review 时间、高风险精确率及 Phase 1 的独立直接调用精度，仍需各自的独立实验，不能由本协议替代。

## 运行后的诊断扩展（不改写原测量）

2026-10-07 首轮测量暴露真实仓库集合不一致后，增加 `SemanticPerformanceProbe --diagnose <原报告> <新诊断文件>`：与已归档全量快照比较关系类别、仓内已解析调用和匿名 UUID 归一化差异。它是单独的非计时诊断，既不替换五次样本，也不把全量输出当作真值；诊断版测试类在正式负载结束后才重新编译。

`node --import tsx scripts/performance-fact-audit.ts <原始证据目录>` 对归档全量快照做只读结构审计，记录符号归属与关系证据路径冲突、未修改文件指向修改文件的调用。新审计文件使用独占创建，禁止覆盖原结果。审计并非新增压测样本，也不测量审查页面的实际召回或质量。

## v5 正确性修复后的复测约束

2026-10-07，使用新的 run2 输出目录保留完整复测，不覆盖 run1。输入提交、受控文件内容、512 MiB 堆、五次配对和 HTTP 波次口径不变；被测适配器由 v4 升级 v5，缓存键按版本隔离，旧快照不复用。运行前先验证新增回归在旧实现失败、修复实现通过。

允许的启动工具调整仅为：有界十秒等待服务的 localMode/protocol 就绪状态，未就绪即明确报错并保留日志；这不改变正式负载入口、并发保护和计时口径。工作台隔离测试也补充子进程失败诊断、最小环境传递与十秒就绪上限，完整测试上限二十秒；不把增大等待预算本身称为性能改进。

复测验收除了五对集合一致，还检查重复全量/增量摘要稳定、注解来源路径与符号归属零冲突、原缺失调用存在及依赖退化保持 SEMANTIC_PARTIAL。它们是工程正确性约束，不是独立直接调用精确率或人工 Review 收益。

## v6 缓存生命周期修复与 run3

run2 在原 512 MiB 堆限制下，完成三对一致样本后因 Java 堆溢出失败，不能报告五次通过。失败信息从原 exec 输出恢复到 `run2/failure-recovered.json`，不补造完整数据。

本机固定版本库的 `JavaParserFacade` 使用全局 WeakHashMap，但 value 强引用 key TypeSolver，后者持有源码树；新增回归确认 v5 完成索引后缓存非空。v6 使用库公开的 `clearInstances()`，在生产索引会话 finally 中释放缓存；所有本项目符号解析通过跨适配器实例、可中断的生命周期锁串行，避免清理另一个活动解析会话。不会调用 System.gc、反射修改生产库内部字段、扩大堆或将每个样本改成新 JVM。

run3 沿用既定输入/五次采样/512 MiB/HTTP 波次。生命周期锁与释放成本计入索引耗时，吞吐上必须承认同 JVM 符号解析串行。测量工具增加每个完成配对后的 JSON 检查点（在两项计时之外，标注 complete=false，完成全部缓存步骤后才为 true），子进程异常保留 stdout/stderr 和 failure.json。检查点改变了样本之间的少量工具开销，因此跨版本总时长不可当作精确加速结论；同一轮全量/增量配对仍采用相同计时口径。
