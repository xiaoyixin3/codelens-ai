# 受控发布恢复安全契约

状态：只读前置检查已实现；以下可写授权/审计/事务契约为下一实现门槛，尚未提供恢复命令。

2026-10-04 增量：审计存储基础已实现并隔离验证，尚未接入任何恢复执行器或身份
认证。请求/拒绝独立提交，成功审计要求调用方事务；这不意味着以下完整授权、审计
工作流或新鲜度/并发门槛已经完成。部署候选需迁移 021，当前公网仍为 019。

后续增量 java.15：Java 入队已接入共享 PR 事务互斥，内部提供必须持锁的最新 run
复核；使用 READ COMMITTED 和实际插入时间，避免等待前的旧快照/事务时间。
未来恢复执行器仍未接入该互斥，不能把基础完成当作完整恢复并发保护完成。

一次性审批基础增量：内部服务已验证受保护配置的运维 bearer，审批用独立密钥复用
现有 AES-GCM、绑定精确快照、最长 5 分钟。首次使用复用 requested 审计行登记，
同一审批不能重复登记，失败/崩溃后需新审批。这是“一次尝试即用尽”的保守实现，
不要求失败后回收令牌，也不把令牌消费和业务成功合成跨事务原子操作。未来成功
业务与成功审计仍须同事务。尚无真实运维配置/传输或恢复执行器，不提供对外命令。

## 第一阶段只做本地确认

首次可写恢复仅考虑：GitHub 已完成原 Check 与摘要发布，但本地确认失败的暂停任务。
不重新发布、不重新分析、不调用模型、不自动重排队列。远端缺失或无法确定是否发布，
不是可以重发的证明；任何正文、批注、目标 ID 或修订冲突都保持暂停。

只读 `publication-inspect` 现在额外报告 `recovery` 与 UTC `observedAt`。
`candidate_for_authorized_local_confirmation` 只表示本次读取得到的证据通过初筛。
`authorized=false`、`writesAllowed=false`、`automaticRecoveryAllowed=false` 始终不变。
报告不是授权凭证，也不是一致性快照，不得拿旧 JSON 直接执行恢复。

候选必须满足：run 和 queue 都 failed、错误为 PUBLICATION_UNCERTAIN、pipeline 为
当前协议、仍是本 PR 最新 run、base/head 实时匹配、仍持有自己的摘要占用记录；三个
远端操作均 verified_remote；冻结记录可解密且身份正确；冻结 Check/摘要指纹与日志
完全相符、start 已确认并且 Check ID 一致。缺记录、未启用校验、错密钥、服务失败或
本地 Check ID 冲突均拒绝。当前规则刻意不接纳已释放占用记录的任务。

## 授权门槛（内部实现进度见下方，开放验收未完成）

1. 独立运维权限与默认关闭的恢复开关；只读检查权限不得直接转换成写权限。运维主体
   需要由受保护身份或部署权限验证，不接受随意填写一个姓名作为身份认证。
2. 单次审批绑定精确 run/job、安装/仓库/PR、base/head、pipeline、冻结 payload hash、
   三个日志指纹/目标 ID、lease generation 和摘要占用；短时有效、随机 nonce、单次使用。
   原始明文、密文、密钥或用户自由输入的秘密不进入令牌、日志或审计。
3. 每次操作存储审计：已验证主体、审批标识、限定动作、输入证据摘要、时间、拒绝理由
   或成功后状态。失败审计不能被业务事务回滚吞掉；成功审计必须与本地状态更新原子提交。
   审计存储失败即拒绝，不允许先完成恢复再尽力记日志。
4. 审批后再次直接读取 GitHub，核对实际 Check 全量批注、原摘要与当前 base/head。
   没有 GitHub 写入。过期、不确定读、权限变化或冲突立即拒绝。

## 数据库提交门槛（内部实现进度见下方，开放验收未完成）

- 在短事务内锁定/比较目标 run、queue、冻结记录与各日志，并核对最新 run、摘要占用
  和审批绑定值。没有处理中的合法或过期 owner；旧租约不得复活。
- 最新 run 的“查找后再写”必须与同一 PR 的入队路径共享数据库互斥协议，避免并发
  入队越过新鲜度检查；只锁定旧 run 的一行不能阻止新 run 插入。
- 仅对审批绑定的目标日志补本地 confirmed，保存原冻结 summary，完成 queue/run，
  递增 lease generation、清除旧锁和自己持有的摘要占用，并消费单次审批。
- 全部修改与成功审计同一事务，任一步失败全部回滚；并发重复审批仅允许一次提交。
- DB 事务不能跨 GitHub 请求。GitHub revision 与本地提交没有跨系统原子性；应尽量
  缩短读写间隔，但不得宣称绝对无竞态或 exactly-once。后续修订事件仍走新 run。

## 2026-10-04 增量：内部本地确认执行器

此前“执行器未接入”的段落为历史进度；本增量新增非 Bean 的内部执行器，仍没有
API、CLI、环境变量启用或真实运维密钥。没有对公网部署做任何升级。

身份校验先于远端读取；审批仅从实时 Inspector 候选和数据库快照签发。恢复重新
检查候选并校验审批、独立登记 requested，再重读 GitHub，最后在共享 PR 互斥内
锁定 run/job、冻结记录、日志、publication 和摘要占用。再次核对最新 run、精确
绑定与有效期，解密原冻结结果并核验指纹；没有网络调用进入数据库事务。

只补三个 confirmed 日志、原目标引用与原 summary，完成 run/queue、递增租约
代次并释放精确属于该 run 的占用；成功审计在同一事务内。已完成任务不能再次
恢复，两个不同审批也只能有一个提交。实现复用已有 Inspector、指纹、冻结输出、
审批和审计，不调用发布方法、分析引擎、模型或源代码执行。

已知拒绝在业务事务回滚后独立记录。数据库/连接异常可能含未知提交结果，此时
保留 requested 待调查，不盲目追加“失败”或重试；审批仍已用尽。登记后即时过期
也可能留下 requested。未登记成功的重复请求不得给原尝试追加拒绝。开放前仍需
实现受保护入口、前置失败审计、pending 审计调查流程、密钥隔离配置/轮换、真实
备份恢复与进程崩溃/提交响应丢失测试。配置 bearer 不等于人类身份或 MFA。

远端读与本地提交仍非跨系统原子操作；后续 GitHub 编辑/修订不能被本地锁禁止。
与旧 Java、Go、TS 或绕过互斥的写入者混跑不在协议保证内。Phase 0/1 的独立
真实效果评测仍未达退出条件，内部恢复测试不能代替这些证据。

## 2026-10-04 增量：只读尝试调查与提交边界演练

审批对象现在提供非秘密 attemptId，便于在操作前保存调查句柄；它不是凭据。
内部 investigate 要求真实配置的 principal，仅查询该主体的审计。单条查询在
独立只读、5 秒超时事务内返回 requested/denied/committed 的历史状态与当前
本地结构一致性；复用成功审计的 SQL 谓词。没有 GitHub 请求或任何业务写入。

没有终态时始终是 PENDING_INVESTIGATION，不断言回滚；已提交但当前结构变化
时保留“曾提交”的事实并报告结构变化。不存在、其他主体或因保留策略删除的
记录不可区分。所有结果明确禁止自动恢复与审批复用。结构一致不等于重新验证
原审批绑定、冻结明文或当前远端内容，不具有防数据库管理员篡改保证。

真实隔离 PostgreSQL 中，在 JDBC commit 前回滚后报错、或实际 commit 后向
调用方报错，分别验证 pending 与 committed，不重发、不伪造拒绝。并验证提交
事务尚未完成时的调查仍读到 pending，不通过写锁阻塞事务。这是提交边界注入，
不是实际进程杀死、网络丢包或数据库故障转移演练。

仍未开放入口、未升级公网。人工调查 pending 后如何安全终结、前置失败审计、
密钥配置/轮换与真实备份/崩溃演练继续作为开放门槛。调查不能自动删除审计、
解锁任务或重签令牌，也不能替代 Phase 0/1 的独立效果评测。

## 2026-10-04 增量：实际 JVM 终止演练

隔离 PostgreSQL 与测试专用子 JVM 验证三个真实终止点：requested 独立提交后、
业务修改/成功审计尚未 commit 时、实际业务 commit 后但尚未返回调用方时。
仅强制终止本测试创建的 Process 对象，不按进程名或外部 PID 寻找服务。

前两者 requested 保留、成功审计和业务修改没有提交，原 slot/代次/日志/引用
保持；后者 completed、confirmed、递增代次、已释放 slot 与 committed 一起
保留。父进程新连接能重新取得 PR 互斥，调查得到相应 pending/committed，旧
审批在所有断点后均不可复用。审批秘密仅经私有 stdin 管道传入，不进入参数或
日志；故障钩子只在测试源码内，不打入正式 JAR。

三个测试需要显式 integration 和 crash 标志、独立 loopback 测试数据库与已
迁移模式，远端只读结果仍为模拟；未匹配的远端方法会使子进程失败。该演练不
代表整机掉电、数据库 crash/failover、实际网络丢包或真实 GitHub 故障已验收。
公网版本和数据库不变，备份/密钥恢复及运维开放门槛仍需分别完成。

## 2026-10-04 增量：冻结输出与审计的备份恢复

隔离 PostgreSQL 17 中使用真实 pg_dump/pg_restore，新库所有 public 表的按行
排序内容指纹与源快照一致；冻结密文、任务/日志/占用、pending/denied/committed
和不可变触发器保留。原发布密钥另行提供后解密成功，错/缺密钥拒绝且不重新
生成；审批秘密和各密钥不在测试数据库中。快照已含 requested 的审批仍不可复用。

同时验证一个明确反例：先备份、后使用审批，再还原旧备份，requested 不在新库。
复用旧签发密钥时，尚有效的旧审批能再次登记。不能把保留数据库上的唯一约束
承诺为跨历史回滚的一次性保证。恢复后必须保持 API/Worker/恢复入口关闭，
禁止旧/新库写入者并行，重新提供历史发布密钥，并通过受保护运维配置生成全新
审批签发密钥，拒绝所有旧审批；新签发密钥不等于轮换历史发布解密密钥。

恢复队列还可能缺少备份之后的远端副作用、撤销或数据删除，必须隔离调查、
重新只读核验并重施授权的保留/删除控制，不能盲目重放、删锁或自动重签审批。
新密钥拒绝旧审批的内部能力已测，但受保护自动轮换、防回滚控制和真实 trial
数据/密钥恢复尚未上线。该合成演练不是 RTO/RPO、异地备份或正式灾备验收。
